── Top 3 Failure Modes — Root Causes & Fixes ─────────────────────────

┌─────────────────────────────────────────────────────────────────────┐
│ #1  FM4 — Missing implicit filters  (×6, 30% of questions)          │
└─────────────────────────────────────────────────────────────────────┘

Observed behaviour:
  • company_id omitted from simple aggregate queries (Q01, Q05).
  • is_active (soft-delete BIT) never filtered on trip, vehicle,
    vts_exception, route, or location tables (Q02, Q10, Q11, Q14).
  • Spurious created_by='<user_id>' injected from request metadata
    into WHERE clause (Q06, Q16) — request field treated as data filter.

Root causes:
  (a) No default_filter / implicit_filter directive in sql_builder.json
      or entity_behavior.json telling the query-builder to always append
      company_id = {company_id} and is_active = 1.
  (b) Request metadata (user_id) leaking into the LLM context as if it
      were a valid filter value — likely a system-prompt injection or
      token-boundary issue.

Metadata-layer fixes:
  1. Add to sql_builder.json → "implicit_filters": {
       "company_id": "{company_id}",
       "is_active": 1
     } for every tenant-scoped + soft-deletable table.
  2. Document invariants in domain_knowledge.json data_model_notes:
     "Every query MUST include WHERE <table>.company_id = {company_id}.
      Rows with is_active = 0 are soft-deleted and must be excluded."
  3. Sanitise request metadata before injecting into the prompt — add
     a blocklist in entity_behavior.json for keys that must never
     become data predicates (user_id, created_by, session_id, etc.).

FM5 — Enum not applied (Q06):
  • 'en route' → recent_state_id = 30 defined in enums.py but not used.
  • Only Q07 (cancelled → 70) and Q08 (CURDATE) passed enum/date tests.

FM2 — Hallucinated column name (Q15):
  • trip.source_location_id does not exist; actual column is trip.location_id.
  • The LLM invented a plausible-sounding column name.
  • Fix: add column descriptions to enum_dictionary.json or a
    columns_context section in llm_context_package.json with
    exact column names so the LLM cannot hallucinate them.

FM8 — Semantic mapping bypassed (Q20):
  • Both 'gps data'→vts_transaction and 'truck'→vehicle are in
    semantics.json, yet entity-detection asked for an entity name.
  • Fix: Semantic aliases must be injected into the entity-detection
    vocabulary — the two systems need to share a single resolution map.

Spurious metadata filter (Q06, Q16):
  • user_id = 'diagnostic_runner' appeared in WHERE created_by = 'diagnostic_runner'.
  • This is a hidden injection risk: in production, a user_id that
    matches a data value could silently over-filter or under-filter results.
  • Fix: Explicitly exclude request-level keys (user_id, session_id,
    trace_id) from the SQL filter construction pipeline.
